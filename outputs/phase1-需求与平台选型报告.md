# 高新技术企业认定评分测算系统 —— 需求与平台选型报告

> 规则基线：《高新技术企业认定管理办法》（国科发火〔2016〕32号）+《高新技术企业认定管理工作指引》（国科发火〔2016〕195号）
> **版本日期必须随系统一同展示**：本报告全部分值与阈值以上述两文件为准；2025 年起主管部门与核查口径变化（详见 §4.4 风险 R-01）作为**可配置覆盖层**，不得直接改写基线规则。

---

## 0. 摘要与核心结论（一页速览）

| 项目 | 结论 |
|------|------|
| **产品定位** | 不是"算个分"的问卷，而是**"70 分硬线下的达标作战沙盘"**——资格预检（一票否决）+ 四项评分 + 双档区间赋分 + 三态达标判定 + 提分路径 + 材料清单 |
| **目标用户（主）** | 拟申报/复审高新技术企业的**科技型中小企业的项目申报负责人**（第一优先级使用者）；财务负责人、研发负责人为协同填写者 |
| **目标用户（次）** | 科技服务/代理申报机构顾问、园区/孵化器服务人员 → **专业版（机构版）用户** |
| **推荐端组合（唯一主推荐）** | **PC Web 为主 + 移动端响应式（同一套 Web 应用），配套轻量 Web 管理后台** |
| **明确不做** | **不做 App（iOS/Android）、不做微信小程序、不做鸿蒙、不做桌面软件**（理由见 §3.4/§3.5） |
| **MVP 规模** | 12 个功能点，约 **62~72 人日**，**6~9 周**（含备案并行） |
| **成本区间** | 开发 **8~15 万元**（外包口径）/ 自研人力成本约 5~8 万元；运行 **200~600 元/月** |
| **最大技术难点** | 评分规则引擎的**区间赋分与边界条件**（成长性四类边界、Ⅰ/Ⅱ类择高、30 分封顶、严格 >70） |
| **最大合规红线** | ①**不得承诺"包过"、不得暗示官方认定结论**；②企业财务/知识产权属敏感数据；③政策引用须标注文号+条款+版本日期 |
| **差异化核心** | **双档区间赋分 → 三态判定（稳过 / 边缘补强 / 不达标）**，竞品普遍只给单点分数 |

**一句话建议：值得做，且应该做"单端 Web 先行"。**这是一个需求真实、政策刚性、搜索流量明确、竞品普遍做得浅的**低频高价值 B 端工具**场景，Web 单端即可完整承接，任何追加端形态都会带来维护成本而无场景收益。

## 1. 需求概述（五要素）

### 1.1 业务目标

> **一句话表述**：让一家准备申报高新技术企业的科技型中小企业，在 10 分钟内搞清楚三件事——**自己有没有资格报、能打多少分、还差在哪里要补什么材料**，并拿到一份可打印、可内部汇报的自评报告。

可量化的成功指标（MVP 上线后 3 个月）：
- 完成一次完整自评的平均耗时 ≤ 10 分钟，完成率（填完→出报告）≥ 60%
- 自然搜索（"高企评分""高企自评""高新技术企业评分表"等词）贡献 ≥ 50% 的独立访客
- 报告导出率 ≥ 40%（说明产出物被带走、被使用）

### 1.2 目标用户与角色划分

| 角色 | 身份 | 核心诉求 | 使用频次 | 设备 |
|------|------|----------|----------|------|
| **A. 项目申报负责人**（第一优先级） | 企业行政/科技管理/总经办/研发助理 | 快速摸底、向老板汇报、制定补短板计划 | 一年 1~2 次（申报季集中） | **办公 PC 为主** |
| B. 财务负责人 | 财务经理/会计 | 校验研发费用占比、高新收入占比、成长性数据 | 申报季 1~3 次 | PC（Excel/财务软件旁） |
| C. 研发/技术负责人 | 技术总监/研发经理 | 提供知识产权清单、成果转化项、技术领域归属 | 申报季 1~2 次 | PC + 手机查资料 |
| **D. 代理机构顾问**（专业版） | 科技服务/知识产权代理机构项目经理 | 批量测评多家客户、留痕、出白标报告 | 高频（每周数家） | **PC 为主** |
| E. 园区/孵化器服务人员（潜在） | 科技园运营 | 批量摸底园区企业 | 季度性 | PC |

> **发起人 vs 使用者区分**：本项目的"发起人"通常为企业老板或代理机构负责人（诉求：获客线索/降低沟通成本），"使用者"是申报专员与顾问（诉求：算得准、说得清、能导出）。**MVP 必须优先满足使用者诉求**，否则工具会沦为无人用的留资表单。

### 1.3 核心使用场景（按优先级）

| # | 场景 | 触发时机 | 用户状态 | 关键动作 |
|---|------|----------|----------|----------|
| **S1（主场景）** | **申报前自评摸底** | 每年 3~6 月申报季前 1~3 个月 | 办公桌前，手边有财务报表、专利证书清单 | 填资格预检 → 填四大指标 → 看总分与 70 分线 → 导出报告 |
| S2 | **达标差距诊断 / 补短板规划** | 自评后发现分数不够 | 办公桌前，与财务/研发一起 | 看每项失分点 → 看提分建议 → 制定 6~12 个月补齐计划 |
| S3 | **模拟评分 / 方案对比** | 有多个可选动作（如再申请 3 项软著 vs 做产学研协议） | 办公桌前 | 改参数 → 看总分变化 → 选性价比最高的动作 |
| S4 | **材料准备清单生成** | 决定申报后 | 办公桌前 | 按诊断结果导出需准备的证明材料清单，分派给各部门 |
| S5 | **代理机构批量测评**（专业版） | 顾问接新客户时 | 办公桌前 | 多企业建档 → 批量测评 → 出机构版报告 |

> **场景共性**：5 个场景**全部发生在办公桌前、PC 上、长时间（8~30 分钟）连续填表、需要导出产物**。这是本次选型的决定性事实。

### 1.4 关键流程（主流程 S1）

```
进入首页（政策版本+免责声明可见）
  → 【步骤0】资格预检：8 项一票否决条件勾选
       └─ 任一不满足 → 弹出阻断提示 + 说明如何补救 + 允许"仍继续测算（仅参考）"
  → 【步骤1】企业成长性：输入近三年净资产 / 销售收入（万元）
       └─ 系统自动算两个增长率 → 自动分档 → 显示计算过程
  → 【步骤2】知识产权：Ⅰ/Ⅱ类数量、自主研发/受让、技术先进程度、核心支持作用、是否参与标准
       └─ 自动择高取档 + 30 分封顶 + "Ⅱ类仅限使用一次"提醒
  → 【步骤3】科技成果转化：近三年转化项数 → 算年均 → 自动分档
  → 【步骤4】研发组织管理水平：4 个维度按"制度+执行证据"分档
  → 【结果页】双档总分（保守/乐观）+ 三态判定 + 四项对照图 + 70 分线
       └─ 失分项逐条列出：当前档位 / 上一档需什么 / 补什么材料
  → 【导出】生成 PDF 报告（含政策依据、免责声明、版本日期）
  → 【保存】存为方案，可回填、可对比
```

### 1.5 约束条件

| 约束 | 状态 | 本报告的假设值 |
|------|------|----------------|
| 预算上限（开发） | ❌ **未确认** | **假设 8~15 万元；分三档决策见 §4.2** |
| 期望上线时间 | ❌ **未确认** | **假设 6~9 周内上线（备案并行）** |
| 团队人力 | ❌ 未确认 | 假设 1 前端 + 1 后端 + 0.5 产品/UI（3 人小队） |
| 主体资质 | ❌ 未确认 | 假设已有公司主体（企业备案更稳妥） |
| 域名/备案 | ❌ 未确认 | **假设未备案 → ICP 备案 1~3 周是关键路径** |
| 平台倾向 | ✅ 已明确 | 用户明确要求"网站" |
| 维护人力 | ❌ 未确认 | **重要**：政策口径需持续维护，须指定政策维护责任人 |

> 以上 6 项未确认项全部列入 §8 待确认清单；**其中"预算上限"与"政策维护责任人"两项会实质影响方案，必须确认。**

## 3. 平台形态选型论证

### 3.1 目标用户设备习惯四步判断法（结论先行）

| 步骤 | 判断 | 结论 |
|------|------|------|
| **① 画用户状态** | 申报负责人在**办公室工位**，手边摊着财务报表、专利证书、研发项目清单，一次性连续填 8~30 分钟，中途要给老板/顾问看结果 | **桌面/长时操作 → Web 应用优先** |
| **② 判使用频次** | 一年 **1~2 次**（申报季），代理机构顾问高频但也在 PC 上 | **低频 → 装 App 必被卸载；不应做 App** |
| **③ 判人群设备构成** | 企业职能人员 + 代理机构顾问，**企业客户 Windows/浏览器为主**，无 iPhone 偏好、无政企国产化强制要求 | **企业场景 → Web；鸿蒙无必要性** |
| **④ 判关键动作** | 需要**大量表单输入、大屏对照、打印/PDF 导出、与 Excel 数据来回核对**；**不需要**推送唤醒、扫码、蓝牙、摄像头、本地重算力、离线 | **无系统能力依赖 → 浏览器能力完全够用；导出/打印是 Web 强项** |

>
> **误判纠正**：竞品"星企链"做了微信小程序，但那是其"企业服务全平台"的战略产物，其小程序测评只有 9 题粗测、无法承载 30+ 字段的完整测算与报告导出 —— **不能因为竞品有小程序就跟一个**。

### 3.6 跨端/技术形态建议

本项目的正确技术判断是 **"不是跨端问题，而是纯 Web 问题"**：

- **不需要跨端框架**（Flutter / RN / uni-app 一律不引入）——没有第二个原生端要覆盖，引入跨端框架只会增加技术栈与人力。
- **推荐形态**：**服务端渲染（SSR）优先的 Web 应用**，而非纯 SPA。理由：
  1. **SEO 是本项目主流量来源**，政策解读/指标说明页面需要被搜索引擎收录 → 必须 SSR 或静态生成；
  2. 测算页交互重，可用客户端交互增强，但内容页必须可爬取。
- **响应式策略**：移动断点只做"能填完、能看结果"，不做"移动优先"设计。PC 端为设计基准。
- **导出方案**：优先**浏览器打印（`@media print` + A4 排版）+ 服务端 PDF 兜底**，避免客户端 PDF 库增大包体。

## 4. 可行性评估（四维度）

### 4.1 技术可行性

**结论：技术可行（低风险）。核心功能全部可用成熟组件拼装，无自研攻关点；唯一需要认真设计的是【评分规则引擎】的边界处理。**

| 能力 | 方案 | 成熟度 |
|------|------|--------|
| 表单与交互 | 主流前端框架 + 表单库 | 成熟 |
| 评分规则引擎 | **自研规则表 + 纯函数计算层**（见下） | 成熟（逻辑确定，非 AI/非启发式） |
| 报告导出 | 浏览器打印 + 服务端 PDF（如 Playwright/wkhtmltopdf 类） | 成熟 |
| 图表可视化 | 成熟图表库（条形图足够，无需复杂图表） | 成熟 |
| 后台配置 | 规则参数存库 + 计算层读取 | 成熟 |
| 账号（V1.1） | 手机验证码（第三方短信）/ 微信登录 | 第三方 |
| **不依赖** | OCR、支付、地图、IM、音视频、大模型 | — |

#### 4.1.1 核心难点：评分规则引擎

**难点不在算法复杂度，而在"规则的可配置化 + 边界条件的完备性 + 结果可解释性"。**

**必须处理的边界条件清单（缺一即算错）：**

| # | 边界条件 | 处理规则 |
|---|----------|----------|
| B1 | **达标判定** | **严格 > 70**（70 分整 = 不达标）。UI 必须明示"70 分以上（不含 70 分）" |
| B2 | 知识产权数量档位 | **Ⅰ类与Ⅱ类择高取档**：Ⅰ类≥1 → A 档；否则Ⅱ类≥5 → B；Ⅱ类 3~4 → C；Ⅱ类 1~2 → D；0 → E |
| B3 | 知识产权总分封顶 | 含"参与标准"加分后**仍 ≤ 30 分**，需做 `min(30, sum)` |
| B4 | Ⅱ类知识产权复用 | Ⅱ类**仅限使用一次**（复审/重新认定时需排除已用过的），需"是否已用于往期申报"标记 |
| B5 | 成果转化计数 | 近三年**年平均数**；同一成果国内外转化或转化为多个产品/服务/工艺/样品/样机**只计一项** |
| B6 | 成长性·增长率为负 | → **0 分** |
| B7 | 成长性·第一年末为 0 | → **按后两年计算**（通行口径：`增长率 = 第三年/第二年 − 1`；⚠ 该口径存在地区解释差异，**必须可配置 + 在 UI 展示计算过程**） |
| B8 | 成长性·第二年末为 0 | → **0 分** |
| B9 | 成长性·实际经营期不满三年 | 按实际经营时间计算；**刚满一年 → 0 分** |
| B10 | 成长性·分档边界 | ≥35%→9~10；≥25%→7~8；≥15%→5~6；≥5%→3~4；>0→1~2；≤0→0 |
| B11 | 研发费用占比三档 | 判定基准为**最近一年销售收入**：≤5000 万(含)→5%；5000 万~2 亿(含)→4%；>2 亿→3% |
| B12 | 科技人员占比 | ≥10%，按**全年月平均数**计算（月平均 = (月初+月末)/2） |
| B13 | 高新收入占比 | ≥60%（**当年**） |
| B14 | 成立年限 | **≥365 个日历天数** |
| B15 | **区间赋分** | 官方多数评分项为"同档区间赋分"（如"高"=7~8 分），逐项 1 分误差累计可导致**总分 ±10 分浮动** → 必须输出**双档**（保守=下限，乐观=上限） |
| B16 | 知识产权有效性 | 以**获得授权证书**（或授权通知书+缴费收据）为准；须在中国境内授权/审批审定且在有效保护期内；权属人为申请企业 |

#### 4.1.2 规则引擎设计原则（交给全栈研发师的关键约束）

1. **规则数据化**：所有档位阈值、分值区间、上限、边界开关存为**可配置规则表**（后台可改），计算层是**无状态的纯函数**，读规则表出结果 —— 政策口径变化时改配置不改代码。
2. **规则版本化**：每条规则带 `政策文号 + 条款 + 生效日期 + 失效日期`，计算时按"测算基准日"取对应版本，**评估结果快照要记录所用规则版本**（否则历史报告无法解释）。
3. **双档输出**：每个评分项返回 `(保守分, 乐观分)`，汇总后得到双档总分与三态判定。
4. **可解释性**：每个评分项返回 `计算过程`（输入值 → 公式 → 档位 → 分值），财务人员必须能核对。
5. **地区口径为覆盖层**：默认国家基线，地区差异作为 overlay 加载，**每处差异必须标注来源与发布日期**，无官方依据的差异不写入规则库。

#### 4.1.3 计算核心示例（python3）

```python
# -*- coding: utf-8 -*-
"""
高企创新能力评价 · 规则引擎核心片段（示例）
基线：《高新技术企业认定管理办法》国科发火〔2016〕32号
     《高新技术企业认定管理工作指引》国科发火〔2016〕195号
设计要点：1) 双档区间赋分  2) 边界完备  3) 计算过程可解释  4) 规则数据化
"""

# ---------- 企业成长性（≤20 分 = 净资产增长率 10 + 销售收入增长率 10）----------

def growth_rate(y1: float, y2: float, y3: float, full_three_years: bool = True) -> tuple:
    """增长率 = 1/2 ×(第二年/第一年 + 第三年/第二年) - 1
    返回 (rate, 说明)；含 B6/B7/B8/B9 四类边界处理。"""
    if not full_three_years:
        return (0.0, "实际经营期不足三年：按实际经营时间计算；刚满一年计 0 分")
    if y2 == 0:
        return (0.0, "第二年末数值为 0：按 0 分计算（边界 B8）")
    if y1 == 0:
        # 边界 B7：第一年末为 0，按后两年计算
        # 口径说明：仅存在 y2→y3 一段增长，取该段增长率（不取 1/2 平均）
        # ⚠ 该口径存在地区解释差异，必须可由后台规则表覆盖，并在 UI 展示计算过程
        return (y3 / y2 - 1, "第一年末为 0：按后两年计算，rate = y3/y2 - 1（边界 B7）")
    rate = 0.5 * ((y2 / y1) + (y3 / y2)) - 1
    if rate < 0:
        return (0.0, "增长率为负：按 0 分计算（边界 B6）")
    return (rate, "rate = 1/2 ×(y2/y1 + y3/y2) - 1")


def growth_score(rate: float) -> tuple:
    """增长率 -> (保守分, 乐观分)，档位同档区间赋分（边界 B10）"""
    if rate <= 0:   return (0, 0)
    if rate >= 0.35: return (9, 10)
    if rate >= 0.25: return (7, 8)
    if rate >= 0.15: return (5, 6)
    if rate >= 0.05: return (3, 4)
    return (1, 2)   # 0 < rate < 0.05


# ---------- 知识产权数量（≤8 分，Ⅰ/Ⅱ类择高取档，边界 B2）----------

def ip_quantity_score(n_class1: int, n_class2: int) -> tuple:
    """Ⅰ类：发明(含国防专利)/植物新品种/国家级农作物品种/国家新药/
     国家一级中药保护品种/集成电路布图设计专有权
     Ⅱ类：实用新型/外观设计/软件著作权（不含商标）"""
    if n_class1 >= 1:  return (7, 8)   # A
    if n_class2 >= 5:  return (7, 8)   # B
    if n_class2 >= 3:  return (5, 6)   # C  3~4 项
    if n_class2 >= 1:  return (3, 4)   # D  1~2 项
    return (0, 0)                       # E  0 项


def ip_total_score(items: list) -> tuple:
    """知识产权合计（边界 B3：含标准加分后仍封顶 30 分）"""
    lo = sum(x[0] for x in items)
    hi = sum(x[1] for x in items)
    return (min(30, lo), min(30, hi))


# ---------- 科技成果转化（≤30 分，近三年年均，边界 B5）----------

def transformation_score(total_3y: int) -> tuple:
    """近三年年均转化项数 = total_3y / 3（同一成果多形式转化只计一项）"""
    avg = total_3y / 3
    if avg >= 5: return (25, 30)   # A
    if avg >= 4: return (19, 24)   # B
    if avg >= 3: return (13, 18)   # C
    if avg >= 2: return (7, 12)    # D
    if avg >= 1: return (1, 6)     # E
    return (0, 0)                  # F


# ---------- 研发费用占比阈值（边界 B11，判定基准：最近一年销售收入）----------

def rd_ratio_threshold(last_year_revenue_wan: float) -> float:
    if last_year_revenue_wan <= 5000:  return 0.05
    if last_year_revenue_wan <= 20000: return 0.04
    return 0.03


# ---------- 总分汇总与达标判定（边界 B1：严格 > 70）----------

def evaluate(ip_items, tf_total_3y, rdmgmt_items, net_assets, revenues,
             full_three_years=True) -> dict:
    ip_lo, ip_hi = ip_total_score(ip_items)
    tf_lo, tf_hi = transformation_score(tf_total_3y)
    rd_lo = sum(x[0] for x in rdmgmt_items)
    rd_hi = sum(x[1] for x in rdmgmt_items)

    na_rate, na_note = growth_rate(*net_assets, full_three_years=full_three_years)
    sr_rate, sr_note = growth_rate(*revenues, full_three_years=full_three_years)
    na_lo, na_hi = growth_score(na_rate)
    sr_lo, sr_hi = growth_score(sr_rate)

    low  = ip_lo + tf_lo + rd_lo + na_lo + sr_lo
    high = ip_hi + tf_hi + rd_hi + na_hi + sr_hi

    # 三态判定：严格 > 70 分（不含 70 分）
    if low > 70:      verdict = "稳过（保守估分已达标）"
    elif high > 70:   verdict = "边缘·需补强（乐观估分达标，保守未达标）"
    else:             verdict = "不达标（需重点补短板）"

    return {
        "score_low": low, "score_high": high,
        "verdict": verdict,
        "detail": {
            "知识产权": (ip_lo, ip_hi),
            "科技成果转化": (tf_lo, tf_hi),
            "研发组织管理": (rd_lo, rd_hi),
            "净资产增长率": (na_lo, na_hi, f"{na_rate:.2%}｜{na_note}"),
            "销售收入增长率": (sr_lo, sr_hi, f"{sr_rate:.2%}｜{sr_note}"),
        },
        "policy_version": "国科发火〔2016〕32号 / 国科发火〔2016〕195号",
        "disclaimer": "本结果为自评测算参考，不构成官方认定结论，最终以认定机构评审为准。",
    }


# ---------- 自检用例 ----------
if __name__ == "__main__":
    r = evaluate(
        ip_items=[(7, 8), (7, 8), (7, 8), (6, 6), (2, 2)],  # 技术先进/核心作用/数量/获得方式/标准
        tf_total_3y=15,                                       # 三年 15 项 → 年均 5 → A 档
        rdmgmt_items=[(6, 6), (6, 6), (4, 4), (4, 4)],
        net_assets=(1000, 1200, 1500), revenues=(2000, 2600, 3500),
    )
    print(r["score_low"], r["score_high"], r["verdict"])
    # -> 保守 30+25+20+7+7=89（示例值，实际按真实档位），乐观更高；verdict 应为"稳过"
```

| 新每创 · 高企申报自评工具 | 网页 | 较完整：8 项评分 + 必备条件检查 + **成长性倒推表** + 保存方案 + 打印导出 | 分子项细，**未做区间双档**（只给单点分）；部分表述（"Ⅰ类权重 45%-50%"）缺官方出处；强留资转化 |
| 宏德雨 · 高企自评 | 网页 | 10 题标准问卷 | 只有 10 题，**无资格预检、无成长性自动计算**（需用户自填赋值）；纯单点分；无导出 |
| 新疆科创网 · 高企评测表 | 网页 | 含基本信息 + 成长性赋值 | **成长性需用户自填"赋值"**（未自动算）；无诊断建议；地域性强 |
| 广正知产 · Excel 评分表 | **Excel 下载** | 有"就低/就高双重估分"意识 | **Excel 形态**：无校验、无引导、无材料清单、易版本失控；但**"就低/就高"思路值得借鉴** |
| 大量代理机构文章页 | 内容页 | 政策解读 | 有流量但无工具，转化靠留资 |

### 6.2 竞品共性短板（= 我们的机会）

1. **83% 的竞品不做"资格预检"**（只算 100 分，不检查注册满 365 天、科技人员 ≥10%、研发费用占比、高新收入 ≥60% 等 8 项一票否决条件）→ **企业最该先查这个**。
2. **几乎全部只给单点分数，不处理"专家区间赋分"** → 官方大量评分项是"7-8 分""25-30 分"的区间，逐项 1 分误差累计 **±10 分**，而 **70 分是硬线**，单点分对 70 分附近的企业毫无指导意义。
3. **成长性要么让用户自填赋值，要么公式/档位写错** → 这是最容易算错、也最容易建立专业信任的地方。
4. **无政策溯源**：普遍不标注规则出自哪条哪款、不标政策版本日期。
5. **无"从分数到材料"的映射**：算出差 5 分，用户仍不知道要准备什么。
6. **多为代理机构子页面，SEO 与产品力都弱**，且强留资打断体验。

### 6.3 差异化切入点（4 条，按性价比排序）

| # | 差异化点 | 用户价值 | 实现成本 | 优先级 |
|---|----------|----------|----------|--------|
| **D1** | **双档区间赋分 → 三态判定**（稳过 / 边缘需补强 / 不达标） | 70 分线附近的企业终于知道自己"稳不稳"，而非一个虚数 | **低**（同一引擎多输出一档） | **MVP** |
| **D2** | **资格预检前置并强阻断**（8 项一票否决 + 补救路径） | 避免不具备资格却白忙一年 | 低 | **MVP** |
| **D3** | **每项失分 → "上一档需要什么" + 需补材料**（差距诊断与提分建议） | 从"差几分"到"做什么" | 中（主要是**内容建设**） | **MVP** |
| **D4** | **政策溯源 + 版本可见**（文号+条款+版本日期，计算过程透明可核对） | 财务/顾问敢信、敢拿去汇报 | 低 | **MVP** |
| D5 | 提分模拟器（改变量看总分变化 + 提分动作性价比排序） | 选最优补齐动作 | 中 | V2.0 |
| D6 | 机构版多企业批量测评 + 白标报告 | 代理机构刚需，付费点 | 高 | V1.1 |

> **差异化定位一句话**：**行业里大家在做"算分计算器"，我们做"70 分硬线下的达标作战沙盘"。**

## 9. 结论与建议（唯一结论）

### 9.1 值不值得做？

**✅ 值得做。** 依据：
1. **需求真实刚性**：70 分是硬线，企业每年必须自评一次，政策复杂到"不借助工具算不清"，且算错的代价是错过一年税收优惠（企业所得税 15% vs 25%）。
2. **竞品普遍做得浅**：现有工具多停留在"10 题问卷给个总分"，**无一同时具备"资格预检 + 双档区间 + 政策溯源 + 提分路径"**，差异化空位明确（§6.2）。
3. **流量入口清晰**：搜索需求明确且竞品 SEO 弱，独立站有机会。
4. **成本可控**：65 人日 / 8~13 万元 / 6~9 周，属中小项目量级，**单端 Web 没有多端成本陷阱**。
5. **无合规禁入项**：只要守住 §5.2 七条边界。

### 9.2 最终推荐（唯一结论）

> ## 🏆 **推荐：PC Web 单端先行（响应式覆盖移动端浏览器）+ 轻量 Web 管理后台**
>
> **推荐端组合（唯一）**：**PC Web 应用（设计基准 ≥1024px，向下响应式至 375px）+ Web 管理后台（同一技术栈）**
>
> **理由（三条）**：
> 1. **用户在哪**：目标用户 100% 在办公桌前、PC 上、连续填 8~30 分钟、需要打印/PDF 导出 —— 浏览器是唯一完全匹配的形态；
> 2. **流量从哪来**：这类工具的主流量是搜索引擎（"高企评分表""高新技术企业自评"），**App 商店在此场景完全失效，小程序无法承接完整测算与导出**；
> 3. **成本与时效**：政策口径处于变动期，规则需**随时热修**；网站可秒级生效，App/小程序的审核周期与之直接冲突，且低频（一年 1~2 次）装 App 必被卸载。
>
> **明确不做**：App（iOS/Android）、微信小程序（MVP）、鸿蒙、桌面软件、公众号 H5 产品端。
>
> **备选方案（仅两种切换条件）**：
> - **条件 A（预算 < 3 万元）** → 切换为"静态政策解读站 + 可下载 Excel 评分表"（3~10 人日）先验证需求，跑通后再升级为 Web 应用；
> - **条件 B（V2.0，且同时满足：移动端访问占比 > 40% + 明确微信内分享需求 + 有稳定运营人力）** → 追加**微信小程序轻量版**（仅资格预检 + 6 题粗测 + 结果查看，**完整测算与导出仍引回 Web**）。
> - **除以上两种条件外，不追加任何端形态。**

### 9.3 三条给下游的硬性输入

1. **给产品主理人**：MVP **12 个功能点**（§2.3），其中 **F6 双档区间赋分 + 三态判定**是差异化核心、**F1 资格预检**必须前置并强阻断、**F11 政策溯源与免责声明**是合规底线，三者不可砍。
2. **给全栈研发师**：**规则引擎是本项目唯一技术攻关点** —— 必须做到"规则数据化 + 版本化 + 双档输出 + 计算过程可解释"，并为 B1~B16 十六条边界建立独立单元测试（§4.1）。技术栈选择以 **SSR 优先**（SEO 是主流量来源）。
3. **给上线发布师**：**ICP 备案必须在项目第 1 天启动**（1~3 周，关键路径）；网站命名须规避"中国/国家/官方"等字样；无应用商店审核周期是本项目优势。
